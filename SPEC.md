# Feature: Host can name each "Bidrag" in a room (instead of "Bidrag 1..5")

## Goal

When the room creator (host) creates a room, they can optionally provide custom names for the entries currently labeled "Bidrag 1..5". These names must be stored with the room and shown consistently on Vote + Results pages for all participants.

## Current behavior (assumed)

- UI renders "Bidrag 1..5" labels hardcoded / generated by index.
- Backend stores room + votes, but not entry names.

## Desired behavior

- Room has an array of entry objects (or strings) that define the labels:
  - default: ["Bidrag 1", "Bidrag 2", "Bidrag 3", "Bidrag 4", "Bidrag 5"]
  - host can override each label at room creation
- All clients render labels from the room data, not from a local hardcoded loop.

## Data model changes

### Room

Add one of these (choose simplest given existing code):
Option A (simple): room.entries: string[] (length 5)
Option B (future-proof): room.entries: { id: string, name: string }[] (length 5)

Constraints:

- Exactly 5 entries for now (keep current app behavior)
- Trim whitespace
- Empty string => fallback to default "Bidrag N"
- Limit length per name (e.g. 40 chars)
- Use my existing endpoints and file structure; don’t introduce new frameworks.”
- Keep existing vote keys bidrag-1..5 unchanged; only add labels.

## API changes

### 1) Create Room (HOST ONLY)

POST /api/rooms
Body may include optional entries:
{
"hostUserId": "string",
"entries": ["string", "string", "string", "string", "string"] // optional
}

Server behavior:

- If entries missing: use defaults
- If entries present:
  - sanitize + validate
  - apply fallback on blanks
- Persist entries with room
  Return:
  {
  "code": "ABC123",
  "entries": [...]
  }

### 2) Fetch room config (needed by vote/results pages)

If not existing, add:
GET /api/rooms/:code
Returns:
{
"code": "ABC123",
"entries": [...]
}

If there is already an endpoint that returns room info, extend it to include entries.

### 3) Votes endpoint

No change to payload format unless current votes structure depends on "bidrag-1..5" keys.

- Keep the existing keys ("bidrag-1".."bidrag-5") for now to avoid migrations.
- Only change the LABEL shown to the user.

## Frontend changes

### Host flow

- On the "create room" screen/page, add 5 input fields:
  - placeholders: "Bidrag 1" ... "Bidrag 5"
  - optional: allow blank (blank => default)
- When host clicks "Create room":
  - include `entries` array in POST /api/rooms

### Vote page rendering

- Replace hardcoded "Bidrag i" rendering:
  - Fetch room config first (GET /api/rooms/:code OR include entries in join response)
  - Render each bidrag title using entries[i]
- Keep the underlying identifiers stable:
  - container id stays `bidrag-1`...`bidrag-5`
  - data attributes stay the same

### Results page rendering

- Use the same entries array to label totals.
- Ensure entries are shown even if someone refreshes (i.e. fetched from server).

## Backwards compatibility

- For existing rooms without entries (if any can exist):
  - server should return defaults when entries missing in DB
- If DB migration is needed:
  - add a migration or a safe runtime fallback

## Acceptance criteria

- Host can set custom names when creating a room.
- Participants see those names on Vote + Results pages.
- Refreshing pages keeps the names (they come from backend, not local state).
- Blank host inputs fall back to "Bidrag N".
- Validation prevents huge strings / invalid types.
- Existing vote logic continues working unchanged.
